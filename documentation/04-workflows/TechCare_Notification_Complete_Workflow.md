# TechCare — Notification & Communication Complete Workflow

> **Document Type:** Cross-System Workflow Specification  
> **Module:** Notifications & Communication  
> **Platform:** TechCare Healthcare Web Application  
> **Audience:** Backend, Frontend, QA, DevOps, Product/Admin  
> **Architecture Context:** ASP.NET Core Web API + Frontend + Relational Database  
> **Scope:** Centralized notification infrastructure shared by Patient, Doctor, Nurse, Pharmacy/Pharmacist, Laboratory, Blood Donor, and Admin modules.

---

## 1. Purpose

The Notification module is the shared communication layer of TechCare. It converts business events generated by other modules into reliable, secure, understandable notifications delivered to the correct recipient through one or more supported channels.

The module must support:

- In-app notifications.
- Email notifications.
- SMS notifications where enabled.
- Future push/mobile notifications.
- Notification preferences.
- Read/unread state.
- Delivery state and retry handling.
- Priority levels.
- Expiration and deduplication.
- Deep links to the related feature.
- Security-sensitive alerts.
- Operational alerts for providers and admins.
- Bulk notifications where authorized.
- Auditability.
- Template management.
- Localization readiness.
- Arabic RTL-ready message content.

The notification system is **event-driven from the business perspective** and **provider-agnostic from the delivery perspective**.

---

# 2. Core Design Principle

Other modules should **not** directly send emails, SMS, or manipulate the notification database.

Instead:

```text
Business Action
     ↓
Domain / Application Event
     ↓
Notification Orchestrator
     ↓
Preference Check
     ↓
Template Rendering
     ↓
Notification Record
     ↓
Delivery Job / Queue
     ↓
Channel Provider
     ↓
Delivery Result
     ↓
Retry / Failure / Audit
```

Example:

```text
Patient books Doctor
        ↓
AppointmentCreated
        ↓
Notification Orchestrator
        ↓
Create notification for Doctor
        ↓
Respect Doctor preferences
        ↓
In-App + Email
        ↓
Doctor receives request
```

---

# 3. Notification Goals

The system must make sure that:

1. The right user receives the right message.
2. A user never receives confidential information they are not authorized to see.
3. Important notifications cannot silently disappear.
4. Temporary provider failures do not destroy the notification.
5. Duplicate business events do not create uncontrolled notification spam.
6. Users can control non-critical notifications.
7. Security-critical notifications follow stronger delivery rules.
8. Every important notification can be traced to the source event.
9. The application remains usable even when an external messaging provider is unavailable.
10. Notification logic remains reusable across all TechCare modules.

# 6. Priority Levels

Use four levels:

```text
LOW
NORMAL
HIGH
CRITICAL
```

## LOW

Examples:

- Promotional/system informational messages.
- Non-essential reminders.
- General tips.

## NORMAL

Examples:

- Appointment accepted.
- Order accepted.
- Result published.

## HIGH

Examples:

- Appointment will expire soon.
- Home collection is approaching.
- Payment failure requiring action.
- Verification issue.

## CRITICAL

Examples:

- Security compromise.
- Mandatory account action.
- Critical operational alert.

The exact use of CRITICAL must be restricted to prevent alert fatigue.

# 7. Delivery Channels

## 7.1 In-App

This is the primary channel.

Requirements:

- Persist notification in database.
- Show in notification center.
- Support unread count.
- Support read/unread state.
- Support action/deep link.
- Support timestamps.
- Support pagination.

## 7.2 Email

Used for:

- Account verification.
- Password reset.
- Security events.
- Important transactions.
- Appointment lifecycle where enabled.
- Lab result availability where enabled.
- Payment receipts.

## 7.3 SMS

Use sparingly and preferably for high-value events because cost and provider reliability may vary.

Examples:

- OTP.
- Critical appointment updates.
- Important delivery or collection reminders.
- Security alerts.

OTP is part of authentication but should reuse the same underlying messaging infrastructure where practical.

## 7.4 Push Notification

Future mobile channel.

The notification model should be designed to add push later without changing business logic.

# 8. Notification Preferences

Each user can control non-critical notification categories and channels.

Suggested preference dimensions:

```text

Channel
Enabled
QuietHours
Language
DigestMode
```

Example:

```text
Appointment + InApp = ON
Appointment + Email = ON
Appointment + SMS = OFF
Promotion + Email = OFF
Security + Email = ON (cannot be disabled)
```

Critical security notifications must not be disabled through ordinary user preferences.

---

# 9. Preference Rules

Preference evaluation sequence:

```text
Is event mandatory?
    ├── YES → bypass ordinary preference for required channel(s)
    └── NO
          ↓
Check category preference
          ↓
Check channel preference
          ↓
Check quiet hours
          ↓
Check user contact availability
          ↓
Create delivery plan
```

Never interpret disabled email as disabled in-app for mandatory transactional notifications.

# 16. Five-Minute Expiration Notification

The five-minute window is a business rule for provider response, not appointment duration.

Required events:

```text
Request Created
Request Reminder Soon
Request Expired
```

Recommended sequence:

```text
created_at
     ↓
calculate expires_at on server
     ↓
queue expiration monitoring
     ↓
approaching-expiry notification
     ↓
provider responds OR expiration occurs
```

Never calculate expiration from the client clock.

# 38. Template Safety

Never render untrusted raw HTML into notifications.

Template variables should be escaped.

Do not allow user-controlled input to become executable HTML, JavaScript, or unsafe links.

# 39. Deep Links

Every actionable notification should optionally include a deep link.

Examples:

```text

/orders/{id}
/lab/results/{id}
/blood/requests/{id}
/wallet/transactions/{id}
```

# 40. Object-Level Authorization

Critical rule:

```text
NotificationId + authenticated user
       ↓
Check ownership / authorized membership
       ↓
Only then return details
```

Never allow:

```http
GET /api/notifications/{someone-elses-id}
```

to expose another user's notification.

This protects against IDOR/BOLA.

# 46. Background Job Architecture

Do not send external messages synchronously inside critical transactional requests unless absolutely necessary.

Preferred flow:

```text
HTTP Request
   ↓
Business Transaction
   ↓
Persist business change
   ↓
Create outbox event
   ↓
Commit
   ↓
Background processor
   ↓
Notification service
   ↓
Delivery provider
```

This prevents a messaging outage from breaking the main appointment/order workflow.

---

# 47. Transactional Outbox

Recommended architecture for reliability.

Entity:

```text
OutboxMessage
-------------
Id
Type
Payload
OccurredAt
ProcessedAt
RetryCount
Status
LastError
```

Example:

```text
Appointment accepted
       ↓
DB transaction writes appointment + outbox row
       ↓
Commit
       ↓
Worker reads outbox row
       ↓
Publishes event
       ↓
Notification orchestrator creates notification
```

This significantly reduces the risk of losing notifications after successful business actions.

---

# 48. Idempotency

Every notification-producing event should have a stable event identifier.

Recommended uniqueness concept:

```text
SourceEventId + RecipientUserId + Channel/EventKey
```

Example:

```text
AppointmentAcceptedEvent-123
```

should not create the same notification 10 times if the consumer retries.

---

# 49. Deduplication Key

For reminder notifications, use a deterministic key.

Example:

```text
appointment-reminder:{appointmentId}:1h
```

Then enforce uniqueness.

This prevents duplicate reminders when the background worker runs multiple times.

---

# 50. Retry Strategy

Temporary delivery failures should be retried.

Example backoff:

```text
1st failure → 30 sec
2nd failure → 2 min
3rd failure → 10 min
4th failure → 30 min
5th failure → dead-letter / permanent failure
```

Exact timings can be configuration values.

Do not retry permanent failures indefinitely.

---

# 51. Failure Classification

## Temporary

Examples:

- Provider timeout.
- Network error.
- Temporary provider outage.
- HTTP 429.
- 5xx provider error.

Action:

```text
Retry with backoff
```

## Permanent

Examples:

- Invalid email address.
- Invalid phone number.
- Destination rejected permanently.
- Unsubscribed channel where notification is non-mandatory.

Action:

```text
Mark failed/skipped
Record reason
Do not retry forever
```

---

# 52. Dead Letter Handling

Failed jobs exceeding retry limit should be placed in a dead-letter mechanism.

Admin should be able to inspect:

- Event id.
- Notification id.
- Recipient.
- Channel.
- Failure code.
- Attempt count.
- Timestamps.
- Provider response summary.

Sensitive payload must be masked.

# 81. Race Condition: Duplicate Event

Scenario:

```text
Consumer receives AppointmentAccepted twice
```

Expected:

```text
One logical notification
No duplicate spam
```

Protection:

```text
Unique(DeduplicationKey)
```

plus idempotent event processing.

---

# 82. Race Condition: Cancel vs Reminder

Scenario:

```text
Appointment cancelled
       ↕
Reminder worker runs at same time
```

Correct design:

- Reminder job starts.
- Worker queries current appointment state.
- Cancellation state is detected.
- Reminder delivery is skipped.

Use proper transaction/isolation strategy where necessary.

---

# 83. Race Condition: Read vs Delete

Mark-read and delete should be idempotent.

Deleting an already deleted notification should return a controlled response instead of corrupting state.

---

# 84. Security: Notification ID Guessing

# 85. Security: Deep Link Manipulation

A deep link must never grant access.

Example:

```text

```

---

# 86. Security: Template Injection

For user-generated names/messages:

```text

```

according to the channel.

# 87. Security: Email Account Compromise

The actual secure action must require authentication and appropriate authorization.

# 88. Security: SMS Privacy

### Correct
Persist event/outbox and send asynchronously.

### Correct

### Correct
Use a generic secure notification.

### Correct
Classify temporary vs permanent failures.

### Correct

### Correct
Re-authorize every source resource.

# 163. Final System Rule

The Notification system should be treated as a **shared infrastructure service**, not as a feature owned by one business role.

The correct responsibility split is:

```text
Business Module
    = decides WHAT happened

Notification Module
    = decides WHO should be notified,
      HOW to notify them,
      WHEN to deliver,
      WHAT safe template to use,
      and HOW to handle failures
```

However, authorization for the underlying business resource always remains owned by the relevant domain module.
